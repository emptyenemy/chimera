# Roadmap

## Готово

- **UI (PySide6 / QWebEngineView, pywebview / WebView2 или вкладка в браузере)** — графический интерфейс, выбор режима и движка через `config.json` (`interface`, `ui_backend`). Вызовы фронта исполняются в фоновых потоках, окно не фризит на долгих операциях (опрос адаптеров, состояние прокси).
  - фронт — компоненты shadcn/ui (new-york, тёмная тема) на чистых HTML/CSS/JS без сборки: ядро `ui/web/js/core.js` (мост, стор, `morph()` — точечный патч DOM вместо перерисовки, роутер страниц, диалоги/тосты/меню/лог), дизайн-система `ui/web/css/base.css`, по файлу на страницу в `js/pages/` и `css/pages/`, иконки lucide спрайтом (`vendor/update-vendor.sh`);
  - состояние модулей фронт не опрашивает: его пушит хаб `ui/hub.py` (по потоку на источник, пуш только при изменении, ленивые источники — пока открыта их вкладка, после команды источник перечитывается сразу). Интерфейс рисует из стора и не ждёт бэкенд; тумблеры переключаются оптимистично и откатываются при ошибке;
  - проверка без окна — `tools/ui_preview.py` (сервер движка browser с настоящим Api, команды не исполняются) + `tools/ui_shot.mjs` (headless Edge по CDP: сценарий кликов, eval, скриншоты);
  - `browser` — своего окна нет: фронт отдаёт локальный HTTP-сервер (`ui/backend_browser.py`, только стандартная библиотека), страница открывается вкладкой в браузере по умолчанию. Мост — `POST /api` (тот же JSON-RPC) и long-poll `GET /events` вместо push'ей; доступ по одноразовому токену (адрес + cookie), потому что через мост доступно всё API. Вкладка закрыта дольше полутора минут — программа гасит свои процессы и выходит, как по закрытию окна.
- **Источники и обновления (Настройки)** — версии всех внешних компонентов в одном списке: сверка с апстримом по каждому отдельно или всех сразу (результаты приезжают по мере готовности — медленный ответ не держит остальные), кнопка «Обновить» в строке (`git fetch` + checkout тега / `reset --hard` для бандла; для стратегий Flowseal сразу перепорт `tools/port_flowseal.py`) и «Обновить всё». Пиннутые в коде версии (sing-box, шрифты) и Python кнопкой не трогаем — вместе с версией меняется схема конфига.
- **Вкладка Hosts** — наборы подмен IP в системном hosts-файле:
  - тип `dns` — DNS-провайдер (XBOX / Comss / Malw): домены из списков резолвятся через его DoH/UDP, полученные IP пишутся в hosts;
  - тип `static` (`modules/hosts/static_providers.py`) — готовый список записей из файла, без резолвинга; встроенный — «Flowseal (GitHub/Telegram/Discord)», читает `upstream/zapret-discord-youtube/.service/hosts` заново при каждом применении (обновление сабмодуля подхватывается само); нет сабмодуля рядом (собранный exe) — провайдер помечен `available: false` с причиной, без падений; в привязках (`assignments`) static-провайдер включается булевым значением, а не списком доменов, т.к. свои записи несёт сам;
  - применённый набор пишется блоком между маркерами `# >>> chimera-hosts >>>` — снимается/обновляется без следов;
  - чекер: TCP + TLS-handshake по каждой записи (OK / TCP / FAIL + пинг в мс);
  - после записи в hosts автоматически `ipconfig /flushdns`;
  - **фон** (`modules/hosts/background.py`, единый поток, `HostsManager.start_background()/stop_background()`, настройки в `data/hosts.json` → `background`, API `hosts_set_background`): автообновление — периодически (по умолчанию раз в 6 ч, выключаемо) перерезолвливает dns-привязки и переписывает блок только если IP реально сменился; чекер — периодически (по умолчанию раз в 15 мин) прогоняет применённые записи TCP+TLS параллельно и копит health (`hosts_state().health`: alive/total/ratio по каждой привязке); автопереключение (выключено по умолчанию) — если dns-привязка деградировала (<50% живых) два чекера подряд, переключает её на следующий живой провайдер из настроенного порядка, событие — в `hosts_state().last_switch` и `data/logs/hosts.log`.
- **Очистка кэша Discord** (`modules/discord.py`, API `discord_clear_cache`) — как одноимённый пункт `service.bat` у Flowseal: чистит `Cache`/`Code Cache`/`GPUCache` у Discord/PTB/Canary/Development в `%APPDATA%`; в отличие от `service.bat` процесс не закрывает сам — если вариант запущен, отменяет чистку целиком с понятной ошибкой (кого закрыть), не трогая остальные.
- **Вкладка DNS (DNS Jumper внутри программы)** — переключение системного DNS:
  - провайдеры в `modules/dns_jumper/providers.json` (Cloudflare, Google, Quad9, AdGuard, Яндекс, OpenDNS, XBOX, Malw);
  - список всех адаптеров со статусом/IP/текущим DNS, выбор адаптера;
  - пинг всех серверов параллельно, применение/сброс на DHCP через `Set-DnsClientServerAddress`.
- **Списки доменов** (`lists/*.txt`) — единый источник для всех модулей: openai, anthropic, google-gemini, microsoft-copilot, deepl, spotify, notion, youtube, discord.
- **Единая папка рантайм-данных** (`modules/paths.py`) — state.json/логи/сгенерированные конфиги всех модулей лежат в `data/` рядом с программой (`data/logs/` — логи), а не рядом с исходниками модулей; путь переопределяется `CHIMERA_DATA`. Рядом с exe, а не в `%APPDATA%`, — портативность и общий вид для будущего service-режима (работает от SYSTEM). Старые файлы переезжают автоматически при первом обращении.
- **Вкладка Telegram** — [flowseal/tg-ws-proxy](https://github.com/flowseal/tg-ws-proxy) как модуль:
  - ядро (пакет `proxy`) импортируется из сабмодуля `upstream/tg-ws-proxy`, работает в фоновом потоке — без трея/окон апстрима;
  - host/port/secret настраиваются (хранятся в `data/tgproxy.json`, не в git), секрет перегенерируется кнопкой;
  - запуск/остановка из UI, автозапуск вместе с программой, живая статистика соединений;
  - tg://proxy-ссылка: «Подключить в Telegram» / копирование;
  - версия ядра показывается в UI + проверка свежего релиза на GitHub;
  - обновление прокси: `git submodule update --remote upstream/tg-ws-proxy` — новые фишки подтягиваются без правок нашего кода.
- **Вкладка Блокировки** — проверка через [LowderPlay/cheburcheck](https://github.com/LowderPlay/cheburcheck), заблокирован ли домен в реестрах РКН:
  - публичный API cheburcheck.ru (свой код проверки не держим), версия сервиса и дата обновления реестра — в UI;
  - проверка одного домена или целого списка (стримингом), причина блокировки (реестр РКН / CDN / подсеть);
  - повтор при rate-limit (429), чтобы «лимит» вылезал реже.
- **Вкладка Стратегии (zapret2)** — запуск `winws2` с выбранной стратегией обхода DPI:
  - стратегии — `strategies/*.txt` (1 аргумент winws2 на строку, плейсхолдеры путей, метаданные в шапке);
  - портированы все стратегии [Flowseal/zapret-discord-youtube](https://github.com/Flowseal/zapret-discord-youtube) 1.10.3 (winws1 `--dpi-desync` → winws2 `--lua-desync`), генератор — `tools/port_flowseal.py`;
  - fake-блобы и hostlist'ы Flowseal лежат в `strategies/assets` и `strategies/hostlists`, синхронизируются тем же генератором (`sync_resources`) — кроме `*-user.txt` и `ipset-all.txt`;
  - **fake replace**: `ACTIVE_DISCORD_UDP.bin` / `ACTIVE_GAME_UDP.bin` — слоты, в которые копируется выбранный блоб (текущий определяется по SHA256, как в `service.bat`); выбор — селектами в карточке «Фильтры»;
  - лаунчер `modules/winws`: сборка argv, старт/стоп winws2, вывод в лог, очистка при выходе;
  - версия zapret2 (тег сабмодуля) показывается в UI; **zapret2 v1.0.5.2**, бандл `6eb463a` (`NFQWS2_COMPAT_VER=6` совпадает). Апстрим бандла регулярно делает force-push — обновление через `git reset --hard origin/master`, не `pull`.
- **Service-режим** (`config.json` → `"interface": "service"`, либо напрямую `python main.py service ...`, независимо от конфига) — фоновый процесс без окна, поднимает то, что помечено автозапуском (tg/winws/proxy), и держит между перезагрузками:
  - `modules/service.py`: install/uninstall/start/stop/status/run; «служба» — задача Планировщика (BootTrigger, принципал SYSTEM, `RunLevel=HighestAvailable`) по образцу `modules/autostart.py`, без pywin32 и без отдельной службы Windows (SCM);
  - остановка — именованное событие `Global\CHIMERA_Service_Stop` (ctypes), живость — именованный мьютекс `Global\CHIMERA_Service_Running` + pid-файл `data/service.pid` (только для отображения), лог — `data/logs/service.log`;
  - `autostart_modules()` — общая с UI логика автозапуска (раньше жила только в `Api._autostart_all`), делит её `Api.__init__`/`_autostart_all` и `service.run()`;
  - прокси в режиме **PAC** под сервисом не поднимается (пишет системный прокси в HKCU текущего пользователя, под SYSTEM это чужой куст) — только **TUN**, PAC пропускается с записью в лог;
  - единственный владелец процессов в паре UI+служба — служба: если она уже запущена (`app_info().service_running`), UI не поднимает свои автозапуски и не гасит процессы при закрытии окна;
  - фоновые задачи hosts (`HostsManager.start_background()/stop_background()`) сервис поднимает и гасит вместе с остальным.
- **TUI-режим** (`chimera tui`, либо `config.json` → `"interface": "tui"`) — полноэкранный терминальный интерфейс на Textual (`tui/textual_app.py`, вкладки `tui/panes.py`). Это клиент работающей Chimera, как командная строка: свой `Api` не создаёт, процессами не владеет, ходит через канал управления теми же методами, что таблица `modules/cli/registry.py` (`tui/remote.py`); не запущена — поднимает её без окна. Выход (`q`) Chimera не останавливает. Вкладки (цифры 1–9, Tab, мышь, `?` — подсказка): Обзор (тумблеры модулей, «Выключить всё» с подтверждением), Стратегии (поиск, Enter — запуск), Списки (чекбоксы winws/прокси, `e` — правка во внешнем редакторе, применяет наблюдатель за файлами), Прокси (режим, старт/стоп, приложения), Hosts (вкл/выкл, списки провайдеров), DNS (пробное применение с откатом, сброс на DHCP), Telegram (ссылка без секрета), Логи (живой хвост), Настройки. Живое состояние — опрос раз в секунду фоновыми воркерами, во вкладки попадает только изменившееся, тяжёлое (списки, hosts, DNS, логи) опрашивается только у открытой вкладки; нет связи — «нет связи с Chimera» и автопереподключение. Вне терминала или без Textual — откат на простое меню; `chimera tui --simple` запускает прежнее меню цифрами (`tui/app.py`, со своим `Api`). Тесты — Textual Pilot в headless с поддельной Chimera (`tests/test_tui_textual.py`).

## В работе / дальше

- **Списки доменов как полноценная вкладка** — редактирование, включение/выключение списков для набора, и **разные транспорты на список**: один гнать через DNS-подмену, другой — через VPN/прокси, третий — через zapret. Списки = общий слой, поверх него правила маршрутизации.
- **Вкладки в разработке**: Пресеты, Прокси (общий).
- **Hosts/DNS, развитие**: автообновление по расписанию, фоновый чекер, автопереключение на живой провайдер.
- **Изменения применяются на лету — сделано.** Правка списка доменов, смена стратегии и любой другой настройки не требует ручного перезапуска, всё применяется в `Api`, поэтому одинаково работает из окна, CLI и у агентов:
  - winws2 сам перечитывает hostlist и ipset при изменении файла (manual zapret2): смена списков и режима IPSet — перегенерация `list-general-user.txt` и `ipset-user.txt` без рестарта (`WinwsManager.refresh_user_lists`);
  - sing-box подхватывает правку local rule-set за доли секунды без перезапуска (проверено на 1.14.2) — домены и подсети вынесены из конфига в `data/singbox-domains.json` и `data/singbox-ips.json`, файлы заменяются атомарно; в режиме PAC дополнительно переписывается PAC и обновляется WinINet (`ProxyManager.reload_lists`);
  - hosts при правке списка пересчитываются заново (`HostsManager.resync`);
  - правка содержимого списка (`lists_save`) доходит до всех, кто его использует; сбой одного модуля (например, нет прав на hosts) не отменяет сохранение и приезжает в `apply_errors`; удалённый список убирается из подключений;
  - перезапуск остаётся только там, где иначе нельзя, и делается автоматически, если модуль запущен: игровой фильтр и его порты, подмена блоба (winws читает при старте — `Api._restart_winws_if_running`, чужой процесс winws2 не трогаем), продвинутые настройки Telegram-прокси, а также ссылка, режим и приложения прокси, порт и секрет Telegram-прокси; сбой перезапуска не отменяет сохранённую настройку и приезжает в `apply_error`.
- **CLI по умолчанию.** Команда `chimera` — основной способ управления, окно и вкладка браузера запускаются флагами `--window` и `--browser`:
  - один exe: сборка с `--windows-console-mode=attach` (вывод в консоль родителя, окна консоли нет), без манифеста `--windows-uac-admin` — права запрашиваются по требованию, как уже делает `relaunch_as_admin`;
  - запуск без аргументов и без родительской консоли (двойной клик, ярлык) открывает окно, как сейчас; в терминале без аргументов — справка; автозапуск и ярлыки зовут `--window --tray`;
  - CLI — клиент работающей Chimera: в неё встраивается локальный сервер управления на `127.0.0.1` с токеном (основа — `POST /api` из `ui/backend_browser.py`), команды идут через `Api.dispatch`; если Chimera не запущена, CLI поднимает её без окна;
  - вывод для людей и для агентов: `--json`, коды возврата, `--help` у каждой команды; команды `restart`, `update`, `status`, запуск и остановка модулей, проверки, списки, конфиг, логи;
  - команда `chimera path add|remove` и кнопка в настройках добавляют папку программы в PATH пользователя.
  - **Сделано:** команда `chimera` со всеми действиями интерфейса (таблица `modules/cli/registry.py`, тест паритета с `Api` и фронтом, таблица «интерфейс → команда» в `docs/CLI.md`); канал управления на `127.0.0.1` с токеном, проверкой `Host`/`Origin` и явным набором методов; `--json` с полем `schema`, коды возврата 0–3, уровни команд read/app/system, маскирование секретов и `--show-secrets`; журнал `data/changes.log`; `chimera docs` и `chimera agent-info` из кода; `--window` и `--browser`, двойной клик открывает окно; сборка с `--windows-console-mode=attach` без манифеста администратора; автозапуск и запуск после обновления зовут окно явно; скилл `skills/chimera` (своя версия и `CHANGELOG`) и `AGENTS.md` в релизе.
  - **Не сделано в CLI:** канал управления не поднимается в фоновой службе (`service run`), поэтому `chimera` видит только Chimera с окном, а `chimera start` запускает окно в трее, а не службу без окна; сборка Nuitka с режимом `attach` без манифеста, запуск из проводника и терминала реальной сборкой не проверены (проверит дымовой тест релиза); кнопка «Командная строка» в настройках (пока `path add|remove` только командой); `llms.txt` на сайте.
- **Для агентов.** `AGENTS.md` в репозитории и `llms.txt` на сайте: раскладка папок, что безопасно править, доступные команды. Управление, меняющее систему (запуск обхода, hosts, DNS, TUN), включается отдельным явным флагом, чтение доступно по умолчанию.
- **`chimera fix <сервис>`.** Сценарий «почини Discord» одной командой, чтобы агенту не приходилось собирать алгоритм самому: состояние → проверка нужных доменов (`block_check_one`, `chebur_check_one`) → перебор подходящих стратегий с перепроверкой после каждой → включение рабочей → отчёт (`--json`). Если ничего не помогло, откат к прежним настройкам и понятная причина. Куски уже есть в `Api`, не хватает связки.
- **Скилл для агентов** (после CLI): короткая инструкция «вызови `chimera fix <сервис>` и прочитай результат», плюс `AGENTS.md` (его читают почти все агенты). Скилл кладётся в репозиторий или в релиз; формат у разных агентов свой, для каждого отдельно не гарантируем.
- **Бэкапы настроек и откат.**
  - В снимок входят: `config.json`, рабочие настройки модулей в `data/` (прокси, winws, hosts, Telegram-прокси, DNS-провайдеры), пользовательские `lists/*.txt` и `*-user.txt` из `strategies/hostlists`. Логи, бинарники, блобы и файлы обновления не входят.
  - Автоснимок перед каждым изменением через CLI или агента, с пометкой причины; хранится последних N (около 20), старые удаляются. Ручные: `chimera backup create|list|restore <id>|diff <id>` и кнопка в настройках. Перед восстановлением делается ещё один снимок, чтобы оно тоже откатывалось.
  - Восстановление применяется тем же слоем «на лету», без ручных перезапусков.
  - Состояние системы (блок в `hosts`, DNS адаптера, системный прокси, WinDivert) не файл настроек: снимок помнит, что было включено, а откат возвращает это штатными действиями (`hosts_set_enabled(false)`, `dns_reset`, остановка модулей).
  - Секреты (ссылка прокси, секрет Telegram) хранятся только локально, в экспорт и отчёты об ошибках не попадают, в `diff` маскируются.
- **Обмен конфигом — минимальная версия сделана** (экспорт по разделам без секретов, предпросмотр, применение со снимком в data/backups; `chimera config export|import-preview|import`; короткий код и QR не сделаны). Настроил себе — отправил маме, брату, друзьям, у них одним действием стало так же.
  - Конфиг — файл `.chimera` (JSON с версией схемы) или ссылка `chimera://import?...`: стратегия, выбранные списки, режим прокси и приложения, привязки hosts, DNS-провайдер, игровой фильтр. `chimera config export|import`, кнопки «Поделиться» и «Импортировать».
  - **Делиться можно частями.** Конфиг состоит из независимых разделов, и при экспорте, и при импорте каждый включается отдельной галочкой. У друзей другие провайдеры, поэтому настройки обхода DPI им скорее навредят, а прокси работает одинаково у всех, если сервер рабочий.
    - Переносимые (в набор по умолчанию): прокси (режим, списки, приложения; ссылка сервера только по явному выбору), списки доменов, привязки hosts и DNS-провайдеры, Telegram-прокси (без секрета: у получателя он свой).
    - Зависят от провайдера (по умолчанию выключены и помечены предупреждением): стратегия winws, подмена блобов, режим ipset, игровой фильтр.
    - В конфиге разделы подписаны, получатель видит, что внутри, и снимает лишнее до применения. `chimera config export --only proxy,lists`, `chimera config import --skip winws`.
  - Импорт всегда с предпросмотром: что изменится (тот же `diff`, что у бэкапов), перед применением автоснимок, применяется слоем «на лету». Ничего не выполняется: только проверенные схемой поля, пути к файлам и команды отбрасываются.
  - Личное не уходит по умолчанию: ссылка прокси и секрет Telegram в конфиг не входят, включаются отдельным явным выбором («мой сервер для мамы»). Чужие DoH-провайдеры и пользовательские серверы hosts при импорте подсвечиваются и требуют подтверждения: это подмена ответов DNS.
  - Позже: конфиг по ссылке с обновлением (владелец поменял стратегию, у получателей предложение обновиться), только с согласия получателя, без молчаливого применения; каталог «работает у провайдера X» в репозитории, пополняется через PR.
  - Короткий код вида `chimera-7f3k…` вместо длинной ссылки (его можно продиктовать по телефону) и QR-код для передачи на соседний компьютер.
- **Совместимость версий** (конфиги, бэкапы, вывод CLI): у получателя может быть версия старее или новее.
  - В файле конфига и снимка: `schema` (целое, растёт только при несовместимых изменениях), `app_version` автора и `min_app_version` (с какой версии конфиг применим целиком).
  - Схема старее нашей: цепочка миграций `N → N+1`, у каждой свой тест; снимки старых версий восстанавливаются так же.
  - Схема новее нашей или в конфиге неизвестные разделы и поля: неизвестное не применяется и не теряется молча. Предпросмотр делит содержимое на три группы: применится, пропущено (нет в вашей версии, с указанием нужной версии и предложением обновиться), конфликтует. Применить можно только понятное; конфиг с неизвестным обязательным разделом (`min_app_version` выше текущей) не применяется совсем, с понятным текстом.
  - Ссылки на сущности, которых у получателя может не быть, разрешаются по-честному: стратегия по id (набор стратегий зависит от версии Flowseal) — нет её, пропускаем и говорим; встроенный список — по имени, а если нет, пропуск; свои списки и свои DNS-провайдеры едут в конфиге целиком, а не по имени.
  - Правило совместимости для схемы: только добавление полей без смены смысла старых; переименования и удаления — через повышение `schema` и миграцию.
  - CLI и вывод `--json`: в ответе есть `schema`/`protocol`; при рукопожатии с запущенной Chimera CLI новее приложения говорит «Chimera старая, выполните `chimera update`», а приложение новее CLI работает на общем подмножестве. `chimera --version` — первая команда, которую скилл просит выполнить.
- **«Починить» одной кнопкой.** Тот же `chimera fix` в интерфейсе: перебор стратегий под провайдера пользователя (основа — `modules/blockcheck.py` и `blockcheck2` из zapret2) с прогресс-баром, итог — «Discord работает, стратегия N». Результат можно сохранить как конфиг и отправить.
- **`fix` помнит результат.** Найденная рабочая стратегия запоминается локально («у этого провайдера и в этой сети сработала N») и при следующем запуске пробуется первой: полный перебор занимает время.
- **Последняя рабочая конфигурация.** Снимок помечается «проверено», когда проверка выбранных сервисов прошла. Кнопка «Вернуть как работало» откатывает к последнему такому снимку; в истории видно, какое изменение сломало сервис (сравнение соседних снимков).
- **Конфиги под сеть.** Дом, точка доступа с телефона, офис: своя конфигурация под каждую сеть (отпечаток — шлюз/SSID), переключается автоматически при смене сети, с уведомлением.
- **Самолечение в фоне.** Фоновая проверка ключевых сервисов; сервис перестал открываться — пробуется следующая стратегия, стало хуже — автоматический откат, в трее уведомление. Основа — уже существующие чекер и автопереключение hosts.
- **`chimera doctor` — первая версия сделана** (Настройки → Диагностика, `chimera doctor [--report]`, шаблон обращения в issues; проверки: права, WinDivert, чужие процессы, порты, sing-box, системный прокси, служба). Отчёт для issues и для агентов: версии, состояние модулей, результаты проверок, последние строки логов; секреты замаскированы. Шаблон issue просит приложить его.
- **Аварийная кнопка «Выключить всё» — сделана** (кнопка на «Обзоре», пункт в трее, `chimera panic`, очистка забытого системного PAC при старте). В трее и командой `chimera panic`: гасит winws, прокси, TUN, убирает блок из hosts, сбрасывает DNS и системный прокси. Нужна тем, кому «пропал интернет» и не до разбирательств; должна срабатывать и после аварийного завершения (очистка при следующем запуске).
- **Списки и стратегии обновляются отдельно от релиза.** Блокировки меняются быстрее, чем выходит версия: канал обновления только списков доменов и стратегий (файлы из репозитория с проверкой SHA256, проверка раз в сутки, применение на лету), без переустановки программы. Пользовательские правки списков не затираются (слияние, как уже сделано для `lists/` при обновлении). Файл списков подписывается, подпись проверяется отдельно от SHA256: подмена страницы загрузки не должна подменить и файл, и его хеш.
- **Пробное применение с автооткатом — сделано для DNS** (`chimera dns trial`, плашка «Оставить / Вернуть»); для стратегий, hosts и TUN не сделано. Смена стратегии, DNS, hosts или TUN может оставить без интернета. Как «сохранить настройки экрана» в Windows: применяем, проверяем доступность, и если пользователь не подтвердил или проверка не прошла за N секунд, возвращаем как было. Тот же механизм для CLI (`--try 30s`), чтобы агент не мог оставить машину без сети. Проверка — набор контрольных точек (нужные сервисы, DNS, доступность шлюза), а не один сайт, чтобы не откатывать зря из-за одного лежащего ресурса. Это основной путь для `chimera fix` и любых изменений, которые делает агент.
- **«Записать домены сайта» — прототип сделан** (Списки → «Записать домены сайта», `chimera dns record-start|record-stop`, по кэшу DNS Windows; проверено на живом кэше, браузеры с защищённым DNS часть доменов не покажут). Сайт не открывается, а какие домены ему нужны (CDN, API, картинки), неизвестно. Режим записи на 30 секунд: пользователь открывает сайт, Chimera собирает домены запросов (DNS и SNI из уже работающего sniff у sing-box) и предлагает добавить их в список одним нажатием. Главная боль при ведении списков. В предложении домены сгруппированы по назначению (картинки, API, аналитика), трекеры по умолчанию не отмечены, чтобы списки не разбухали.
- **Диагностика конфликтов в `doctor`.** Проверка того, из-за чего обход не заработает: драйвер WinDivert, Secure Boot, нет прав, занятый порт, чужой winws/zapret или `.bat` Flowseal, другой VPN или прокси в системе, антивирус блокирует драйвер, настройки IPv6. Для каждого случая понятный текст и что сделать. Заодно самый частый источник issues.
- **Доверие к сборке.** Подпись exe (для открытых проектов есть бесплатные программы подписи), чтобы SmartScreen и антивирусы не пугали драйвером WinDivert; SHA256 в описании релиза; установка через `winget`/`scoop`; страница «что Chimera отправляет в сеть» (проверка обновлений, cheburcheck, скачивание списков), чтобы это было видно и в README.
- **Автоматика по процессам.** Включать нужный способ, когда запускается конкретная программа (Discord, игра), и выключать, когда закрылась: обход не трогает остальной трафик, когда он не нужен. Основа — `winproc` и выборочный TUN по приложениям.
- **История доступности.** Дашборд помнит результаты фоновых проверок: за неделю Discord был доступен N% времени, вот когда упал и после какого изменения. Уведомления в трее о падении и восстановлении.
- **Семейный режим (по желанию).** У мамы установлена Chimera, у вас нет доступа к её компьютеру, а узнать, что что-то отвалилось, хочется. Уведомление в Telegram или веб-хук владельцу, если фоновая проверка не смогла починить; кнопка «Попросить помощь» кладёт в буфер отчёт `doctor` со ссылкой. Только по явному согласию владельца компьютера, ничего не отправляется по умолчанию.
- **Интеграции для разработчиков и агентов.** MCP-сервер поверх того же канала, что у CLI (чтение по умолчанию, запись включается флагом), автодополнение команд для PowerShell и bash, `chimera watch` для потока событий, `chimera logs -f`.
- **Режим для непосвящённых.** Экран с одной большой кнопкой и словами «Всё работает» / «Discord не открывается — починить», расширенный интерфейс скрыт до включения. Мастер первого запуска: «что у вас не открывается?» → подбор и включение.
- **Сравнение стратегий.** После `fix` таблица «эта стратегия: Discord работает, YouTube нет, скорость такая-то»: пользователь видит, из чего выбрана рабочая, и может выбрать другую.
- **Замер скорости, а не только доступности.** Стратегия может «открывать» YouTube, но давать 200 Кбит/с. Проверка скорости до нужного сервиса отделяет «работает» от «формально работает» и входит в `check`, `fix` и историю доступности.
- **Импорт из других инструментов.** Прочитать существующие настройки Flowseal (`general`, `.bat`) и ссылки подписок для прокси, чтобы проще было перейти с прежнего инструмента.
- **Режим «только проверка».** Вся диагностика без единого изменения и отчёт на выходе (`--dry-run`, `chimera doctor`). Полезно и людям, и агентам перед реальными действиями.
- **Единый журнал изменений.** Кто и когда что менял (окно, CLI, агент), человеческим языком: «вчера 22:10 агент включил стратегию 5». Запись можно откатить. Продолжение бэкапов.
- **Лимит частоты для агентов.** Не больше N изменений в минуту и запрет на «пилу» из включений и выключений: защита от зациклившегося агента.
- **Несколько языков.** Программа, CLI, сайт и документация на нескольких популярных языках. Язык определяется по системе, переключается в настройках и флагом `--lang`.
  - Начать с русского (основной) и английского; дальше по запросам сообщества. Кандидаты: китайский, испанский, турецкий, украинский, персидский. Точный набор уточняется.
  - Тексты интерфейса — каталоги `ui/web/i18n/<язык>.json` с ключами (плюрализация по правилам языка, порядок слов не зашит в код), запасной язык — английский, отсутствующий ключ виден в проверке CI. Для языков с письмом справа налево (персидский, арабский) — зеркальная вёрстка.
  - Важное ограничение: сейчас бэкенд возвращает готовые русские сообщения об ошибках (`_err(e)`, тексты исключений в `modules/`). Нужны коды ошибок с параметрами; текст собирает клиент (окно или CLI) на выбранном языке. Без этого перевод интерфейса будет неполным.
  - `--json` в CLI языко-независим: ключи и коды стабильны, переводится только человекочитаемый вывод.
  - README, сайт и справка CLI переводятся вместе; перевод принимается через PR, шаблон каталога и правила в `docs/`.
- **Восстановление после сбоя.** Chimera упала при поднятом TUN, системный прокси остался на мёртвый порт или в `hosts` остался блок: сеть «провисает». При следующем запуске (и отдельной задачей при старте системы) проверять такие хвосты и чистить; сейчас чистятся только хвосты sing-box.
- **Подписанные обновления программы.** Обновление сверяется по `digest` с той же страницы GitHub, откуда скачано. Подпись релизных файлов ключом, вшитым в программу, закрывает подмену и файла, и его хеша.
- **Защита от утечек в полном TUN.** Если прокси упал, трафик не должен молча пойти напрямую и раскрыть реальный адрес: блокировать до восстановления (kill switch), включается по желанию.
- **Ротация логов.** Логи (`winws.log`, `proxy.log` и др.) растут без ограничения: ограничить размер и число файлов.
- **Несколько прокси-серверов с автовыбором.** Пул серверов, проверка здоровья каждого, переключение на живой или самый быстрый (группы `urltest`/`selector` в sing-box).
- **Подписки на прокси.** Ссылка-подписка на список серверов с автообновлением, как в клиентах v2ray.
- **«Всегда напрямую».** Отдельный список исключений: банки, Госуслуги и другое, что ломается под прокси, особенно в режиме полного TUN.
- **Статистика трафика прокси.** Сколько ушло через прокси за день и месяц, предупреждение при приближении к лимиту сервера.
- **Что изменилось в списках.** При обновлении списков показывать «добавлено 12 доменов, убрано 3» с возможностью посмотреть подробности.
- **Сайт.** Настоящие скриншоты и короткий GIF вместо макета, страница «Что нового» из релизов GitHub, английская версия, раздел «Как это работает» с честным описанием, что программа делает с системой.
- **Устройства рядом (по желанию).** Несколько компьютеров и ноутбуков дома или у друзей видят друг друга в локальной сети и помогают друг другу: «у вас YouTube недоступен, а на устройстве X из вашей сети работает — применить его настройки?». Проверка и починка с телефона. Всё выключено по умолчанию, пользователь сам решает, что и кому видно (кто-то не хочет, чтобы видели его списки и настройки).
  - Обнаружение: mDNS/DNS-SD (`_chimera._tcp`), работает только пока функция включена; неспаренным устройствам не видно ни настроек, ни списков, ни состояния.
  - Спаривание: одноразовый код или QR на первом устройстве, ввод на втором; дальше шифрование с закреплёнными ключами. Локальная сеть считается недоверенной (общежитие, кафе, гости).
  - Видимость по каждому спаренному устройству и разделу: невидимо / только имя и версия / состояние сервисов (без списков и настроек) / можно предлагать и получать конфиг. Списки и настройки показываются, только если владелец разрешил.
  - Подсказка «у X работает»: у устройства сервис не открывается, а у спаренного в той же сети открывается, предлагается применить его конфиг. Та же сеть означает того же провайдера, поэтому здесь разделы, зависящие от провайдера (стратегия winws), в набор по умолчанию входят. Применение только с согласия получателя: предпросмотр, снимок, пробное применение с автооткатом; чужие изменения молча не применяются.
  - Передача конфига «рядом» без мессенджера: код или QR, устройство забирает конфиг прямо по локальной сети.
  - Обзор устройств: кто в сети, версия, работают ли нужные сервисы. Проверить, что у всех дома в порядке, с одного экрана.
  - **Управление с телефона через браузер.** У программы уже есть движок `browser` (`ui/backend_browser.py`): локальный HTTP-сервер с тем же интерфейсом и токеном. Открыть его для телефона в той же сети: на компьютере включается «Управление с телефона», показывается QR со ссылкой и одноразовым токеном, телефон открывает страницу в браузере, всё выполняется на компьютере.
    - Что нужно сделать в коде: вынести сервер и проверку токена из `backend_browser.py` в отдельный модуль, который работает рядом с любым движком окна (сейчас сервер есть только в режиме `browser`); слушать локальную сеть только при включённой функции (сейчас жёстко `127.0.0.1`); для удалённой страницы отключить сторожа «вкладка закрыта — выходим» (`IDLE_TIMEOUT`), иначе закрытая вкладка телефона гасила бы программу.
    - Что должен видеть телефон: не весь интерфейс на десктопных вёрстках (на узких экранах он сейчас не приспособлен: есть только несколько `@media` для сеток, нет мобильной навигации), а отдельная мобильная страница: состояние, «Починить», включение и выключение способов, проверка домена.
    - Ограничения по безопасности: только методы из разрешённого набора (не все 93 метода `Api`; никаких hosts, DNS и TUN без отдельного разрешения), секреты (ссылка прокси, секрет Telegram) маскируются, проверка заголовков `Host` и `Origin` против атак через браузер, токен живёт недолго и отзывается кнопкой, ограничение частоты запросов.
    - Не определено: шифрование. Обычный HTTP по локальной сети позволяет подсмотреть токен на общей сети; HTTPS с самоподписанным сертификатом даёт предупреждение браузера на телефоне. Варианты: HTTPS с подтверждением отпечатка через QR, короткоживущий одноразовый токен без шифрования (приемлемо только дома), привязка к адресу телефона. Выбор не сделан.
  - Порт в локальной сети открывается только при включённой функции; все команды проходят ту же проверку, что импорт конфига; выполнения произвольных команд нет.
  - **Агент и другие устройства.** Агент общается только с Chimera на своём компьютере (CLI или MCP), а она пересылает команду спаренному устройству по тому же зашифрованному каналу: `chimera --device <имя> fix youtube`. Произвольного доступа к чужим машинам у агента нет, только заданный набор действий (`fix`, включение и выключение обхода, смена списков).
    - Отдельный уровень прав «разрешить удалённые команды»: выключен по умолчанию, настраивается по каждому устройству отдельно.
    - По умолчанию согласие на целевом устройстве: агент просит, у владельца всплывает уведомление с предпросмотром, «да» применяет. Автооткат срабатывает на самом устройстве, не дожидаясь агента.
    - Журнал изменений на целевом устройстве: кто, когда и что менял; владелец может откатить.
    - Лимиты: не больше N изменений в минуту на устройство и на агента.
    - Первая версия — только «предложить и подтвердить на месте».
  - **Не определено:**
    - «Доверенное устройство» без вопросов на ограниченное время (например, на час): нужно ли вообще, для каких действий и на какой срок. Замена прокси-сервера и DNS в любом случае не входит.
    - Управление устройствами вне локальной сети (через интернет): потребует сервера-посредника, пока не планируется.
    - Точный набор уровней видимости и их названия.
    - Как обнаруживать устройства (готовая библиотека mDNS или своя реализация на стандартной библиотеке) и как быть с запросом брандмауэра Windows при первом открытии порта (правило создаётся из-под администратора или запрос виден пользователю).
    - Порядок внедрения: предположительно сначала «передать конфиг рядом» по коду или QR без спаривания, затем спаривание и обзор устройств, затем подсказка «у X работает», затем страница для телефона, затем управление агентом.
- **Раздача обхода на телефон, телевизор и приставку.** Устройства, на которых Chimera не запустить, получают обход через компьютер: прокси-порт доступен в локальной сети, плюс адрес PAC-файла для настройки на устройстве. Риск: порт, открытый для всех в сети. Поэтому только по паролю или списку разрешённых устройств, выключен по умолчанию, привязка к внутреннему интерфейсу. Не определено: режим (только PAC для выбранных доменов или весь трафик устройства), нужна ли вообще эта функция, если есть «Устройства рядом».
- **Помощник-агент в программе.** Отложено на неопределённый срок (решение автора). Запустить внешнего агента-помощника прямо из Chimera в папке программы и попросить что-то починить.
  - **Первый уровень: кнопка «Открыть агента в терминале».** Запускает обычный терминал пользователя (Windows Terminal, иначе консоль) в папке программы с заранее заданной командой агента. Терминала в самой программе нет. Дёшево и безопасно. Настройка «Команда агента» (любая команда, которую укажет пользователь), ничего не привязано к конкретному агенту.
  - **Второй уровень: встроенный терминал** на странице программы (xterm.js в окне, на стороне Python псевдоконсоль ConPTY на Windows и `pty` на Linux и macOS), с готовыми запросами вроде «Починить Discord». Заметно больше работы: размер окна, кодировки, копирование, сессии.
  - Общие требования:
    - Терминал и агент запускаются **без прав администратора**, хотя сама Chimera работает с повышенными. Изменения системы агент делает только через CLI и канал управления, где действуют разрешения и автооткат. Иначе встроенный терминал был бы оболочкой администратора внутри программы.
    - Встроенный терминал **никогда не доступен через страницу для телефона и удалённые каналы**: это была бы удалённая оболочка. Только локальное окно.
    - В релизе рядом с программой лежат `AGENTS.md` и скилл, чтобы агент, запущенный в папке программы, сразу видел правила и команды.
    - Секреты (ссылка прокси, секрет Telegram) сейчас лежат открытым текстом в `data/*.json` в той же папке, значит агент может их прочитать, а вместе с ним провайдер модели. Нужно хранить их иначе (защищённое хранилище Windows) или явно предупреждать перед запуском.
    - Учётные данные агента (вход, ключи) остаются у самого агента, Chimera их не видит и не хранит.
  - Не определено: делать ли встроенный терминал вообще или остановиться на первом уровне; рабочая папка агента (папка программы целиком или отдельная, где только логи и `AGENTS.md`); как запретить агенту править файлы программы (полностью запретить не получится, только предупреждать и просить работать через CLI).
- **Попросить агента с телефона.** Настоящая цель терминального сценария: с телефона сказать агенту «почини Discord», а агент работает на компьютере. Терминал для этого не нужен и по сети недопустим (это удалённая оболочка администратора), поэтому варианты другие.
  - **A. Через собственный удалённый режим агента** (у некоторых агентов он есть: сессия на компьютере управляется с телефона средствами самого вендора). От Chimera нужны только CLI, `AGENTS.md` и скилл, в самой программе кода почти нет. Нужно выяснить, какие агенты это умеют.
  - **B. Поле «Попросить помощника» на странице для телефона.** Телефон присылает текст, компьютер запускает агента в неинтерактивном режиме (без оболочки на телефоне), агент ограничен списком разрешённых действий (только команды `chimera`), а вывод стримится обратно на страницу. Доступ к оболочке телефон не получает, но токен телефона фактически позволяет давать задания агенту, поэтому ограничения агента (список команд, песочница) обязательны, а сам запуск требует явного включения.
  - **C. Кнопка «Починить» на странице для телефона** (`chimera fix`) без агента. Закрывает большинство случаев детерминированно; агент нужен для нестандартных.
  - Не определено: выбор между A и B (или оба), набор агентов, которые поддерживаем в B, точные флаги неинтерактивного запуска и ограничения прав у каждого (проверять по документации агента на момент реализации), что показывать пользователю о действиях агента (лента команд в реальном времени и кнопка «остановить»).
- **Встроенный помощник.** У пользователя может не быть внешнего агента (или он его не хочет), поэтому помощник встроен в Chimera: пишешь по-человечески («не открывается сайт X», «добавь всё, что нужно для Y», «почему не работает?»), он разбирается и чинит. Работает и на компьютере, и со страницы для телефона.
  - **Основа без ИИ.** `chimera fix`, диагностика и мастер «что у вас не открывается?» работают без моделей, офлайн и без ключей. Помощник на модели — необязательная надстройка для нестандартных случаев; без неё программа не теряет ни одной функции.
  - **Замкнутый набор инструментов.** Помощник (цикл модели с вызовом инструментов) получает не оболочку, а закрытый набор функций программы: состояние, проверка домена, `fix`, чтение и правка списков, включение и выключение способов, разбор логов и отчёта `doctor`. Работают те же ограничения, что для внешних агентов: уровни прав, предпросмотр, автооткат, лимит частоты, журнал изменений. Поэтому его можно безопасно показывать и со страницы для телефона: произвольных команд нет.
  - **Один набор инструментов на всех.** Те же функции отдаются внешним агентам (MCP-сервер, CLI) и встроенному помощнику: логика и права описаны в одном месте.
  - **Откуда модель** (не определено, варианты):
    - свой ключ пользователя (API вендора или любой совместимый эндпоинт) — по умолчанию рекомендуемый вариант;
    - локальная модель (например, через Ollama): офлайн и приватно, но тяжело по ресурсам и слабее по качеству;
    - размещённая нами служба с моделью: расходы, злоупотребления и вопросы приватности, пока не планируется.
  - **Приватность.** Помощник выключен по умолчанию и включается явным согласием. Перед первым использованием показывается, что уходит модели (домены, статусы, куски логов), секреты (ссылка прокси, секрет Telegram) вырезаются до отправки. Ключ хранится в защищённом хранилище Windows, не в `data/*.json`.
  - Не определено: какие поставщики моделей поддерживаем, нужен ли режим локальной модели с первого выпуска, как оценивать качество ответов помощника (набор тестовых сценариев «почини X»), что показывать пользователю о ходе работы (лента действий и кнопка «остановить»).
- **Переносимое ядро: Chimera на любом устройстве.** Цель — запуск не только на Windows-компьютере, но и на роутерах, мини-компьютерах, NAS и в контейнерах: везде, где работает Linux («на любой микроволновке»). Подробности платформенного слоя — в разделе «Кроссплатформенность» ниже.
  - **Ядро без графики.** Отдельная часть: запуск способов обхода, списки, применение на лету, CLI и API, страница для телефона. Окно Windows, страница для телефона и CLI — клиенты этого ядра. Так одно и то же ядро работает и на ПК, и на роутере.
  - **Что уже переносимо:** `nfqws2` (Linux-вариант `winws2` из zapret2; для OpenWrt в апстриме есть сборка) и `sing-box`. Наше — оркестрация: генерация настроек, списки, применение на лету, логика `fix`, CLI и API.
  - **Главное препятствие:** ядро сейчас на Python, а на роутерах с малой памятью Python обычно не ставят.
  - **Проверка без железа.** Образы OpenWrt (x86-64, armvirt) в QEMU и контейнеры в CI, поэтому сборку под роутер можно тестировать, не имея физического роутера.
  - **Лестница платформ:** 1) обычный Linux (ПК, мини-ПК, Raspberry Pi) на нынешнем Python-ядре; 2) контейнер и NAS; 3) OpenWrt на x86 и ARM; 4) остальные архитектуры (MIPS) — по желанию.
  - **Решение по срокам (автор):** пока остаёмся на Python. Набор нужных и важных функций ещё не определён, а Python быстрее всего для разработки и проверки идей. Переход на другой язык (Rust или Go) начинается, когда набор функций определён и заморожен, найденные ошибки исправлены, а формат настроек и API (`Api.dispatch`, схемы конфигов и снимков) стабилен. После перехода новые функции выходят изредка, в основном исправления ошибок и вклад сообщества.
  - **Что делать на Python уже сейчас, чтобы переход был дешёвым:** держать API и схемы файлов стабильными и описанными; писать тесты, результаты которых потом станут эталоном для сравнения нового ядра; не привязывать форматы данных к особенностям Python; изолировать код, зависящий от ОС, в отдельные модули (платформенный слой). Вынести ядро без графики можно и на Python: это не противоречит переходу.
  - **Не определено:** критерии «заморозки» (конкретный перечень функций и порог качества); как учесть вкладчиков сообщества: Python им проще, чем Rust или Go, и переход может уменьшить число желающих помогать.
  - **Оговорка:** стратегии Flowseal написаны под `winws2` для Windows (WinDivert), для `nfqws2` аргументы частично другие. Перенос стратегий и проверка, что в прошивке роутера есть нужные модули ядра (NFQUEUE), — отдельная работа.
  - **Не определено:**
    - **язык переносимого ядра: Rust или Go**, автор склоняется к Rust. Окончательный выбор не сделан; сравнение:
      - Rust: самый маленький и быстрый файл, нет сборщика мусора, строгие типы и перечисления хорошо ложатся на API «метод → результат или ошибка»; `clap` даёт справку, подкоманды и автодополнение для CLI; `tokio`/`axum` для сервера, `serde` для JSON. Минусы: дольше сборка, круче порог входа, MIPS (частая архитектура роутеров) в Rust имеет «третий уровень» поддержки. Проверено 2026-09-29 по таблице платформ rustc (doc.rust-lang.org/rustc/platform-support.html): `mips-`/`mipsel-unknown-linux-musl` и `-gnu`, а также `mips64*`, все Tier 3 («проект Rust не собирает и не тестирует их автоматически, они могут работать, а могут и нет»), готовой стандартной библиотеки через `rustup` нет, нужна ночная сборка. При этом `aarch64-unknown-linux-musl` — Tier 2 с хост-инструментами, а `armv7-unknown-linux-musleabihf`, `x86_64-unknown-linux-musl`, `riscv64gc-unknown-linux-musl` — Tier 2, то есть собираются готовыми инструментами.
      - Go: проще и быстрее в разработке, сборка под любую архитектуру одной переменной, MIPS в основном наборе (`mips`/`mipsle` — MIPS32r1, `mips64`/`mips64le`; по странице требований Go, проверено 2026-09-29; режим без аппаратной плавающей точки `GOMIPS=softfloat` из документации Go, здесь не перепроверялся), `sing-box` сам на Go. Минусы: файл и память больше, сборщик мусора.
      - Общее: `sing-box` и `nfqws2` в любом случае остаются отдельными процессами (встроить `sing-box` в Rust нельзя), Windows-специфика (WinDivert, hosts, DNS, UAC) уходит в отдельные адаптеры под каждую систему, существующий API `Api.dispatch` сохраняется, чтобы окно и CLI не заметили замены, а результаты Python-тестов служат эталоном для сверки нового ядра.
      - Что решит выбор: нужны ли роутеры на MIPS (тогда Go проще), и на чём автору удобнее поддерживать проект годами.
    - также не определено: переписывать всё ядро в одну переносимую программу или оставить Python на Linux-компьютерах и делать компактное ядро только для роутеров;
    - список поддерживаемых архитектур и прошивок (OpenWrt, Keenetic с Entware, Asus Merlin и др.);
    - способ распространения (пакет `opkg`, скрипт установки, образ контейнера);
    - управление роутером: веб-страница на самом устройстве, приложение-пульт или только CLI.
- **Правки файлов напрямую тоже на лету.** Сейчас применение сидит в `Api` (`lists_save` и подобные), поэтому список, изменённый на диске агентом или вручную, работающая программа не подхватывает. Нужен наблюдатель за `lists/` и `config.json` внутри программы (или обязательный путь через CLI), который вызывает то же применение, что `lists_save`.
- **Порядок работ:** изменения на лету (в работе) → CLI (`--json`, коды возврата, канал управления) → бэкапы и «последняя рабочая» → `chimera fix` и кнопка «Починить» → конфиги и `panic` → `doctor`, конфиги под сеть, самолечение → `AGENTS.md` и скилл (сразу после `fix`, если раньше понадобится).
- **Кроссплатформенность новых частей.** Канал CLI (`127.0.0.1` + токен), файлы правил sing-box и бэкапы не зависят от ОС. Windows-специфика (события `instance.py`, WinINet, `ctypes`, режим консоли Nuitka) уходит в платформенный слой (см. раздел ниже).

## Кроссплатформенность (Linux / macOS)

Цель — вынести всё, что зависит от ОС, в платформенный слой (`modules/platform/` с общим интерфейсом и реализациями win/linux/macos), а ядро (списки, парсеры, менеджеры) оставить общим. Текущий код прибит к Windows: PowerShell-командлеты, `winreg`, `ctypes.windll`, `tasklist`, бандл winws2. Готовность сильно разная по компонентам:

| Компонент | Windows | Linux | macOS | Что нужно сделать |
|---|---|---|---|---|
| Прокси (sing-box) | ✅ | ✅ | ✅ | бинарь под ОС/арх; системный прокси per-OS (`networksetup` / `gsettings`), TUN уже кроссплатформенный |
| Telegram-прокси | ✅ | ✅ | ✅ | готово — чистый Python asyncio |
| Проверки (cheburcheck / blockcheck) | ✅ | ✅ | ✅ | готово — HTTP и сокеты на stdlib |
| DoH/UDP-резолвер | ✅ | ✅ | ✅ | готово — stdlib |
| Hosts | ✅ | ⏳ | ⏳ | путь `/etc/hosts`, flush: `resolvectl flush-caches` (Linux) / `dscacheutil -flushcache; killall -HUP mDNSResponder` (macOS) |
| DNS-переключатель | ✅ | ⏳ | ⏳ | весь ОС-слой заново: `nmcli`/systemd-resolved (Linux), `networksetup` (macOS) вместо DnsClient-командлетов |
| Элевация прав | ✅ (UAC) | ⏳ | ⏳ | на Unix `os.geteuid()`; повышение через polkit/`sudo` (Linux) или `osascript ... administrator privileges` (macOS) |
| UI (PySide6/QWebEngineView) | ✅ | ⏳ | ⏳ | тот же бандленный Chromium на всех трёх ОС (Qt WebEngine) — переносится проще, чем на pywebview с его per-OS нативными вебвью |
| **DPI-обход (zapret)** | ✅ winws2 + WinDivert | ⏳ **nfqws2** | ❌ **под вопросом** | см. ниже |

**DPI-обход — главный затык и он разный по ОС.** На Windows перехват пакетов делает WinDivert; на Linux эквивалент — `nfqws2` через NFQUEUE + правила nftables/iptables (нужен root). Формат стратегий близок (`--lua-desync` тот же), но `--wf-*` (windivert-фильтр) на Linux заменяется правилами NFQUEUE — генератор стратегий и менеджер winws придётся развести по бэкендам. На **macOS нативного механизма нет**: divert-сокеты Apple фактически убрала, NFQUEUE отсутствует, готового zapret под мак нет — без своего kernel-extension (подпись Apple + SIP) полноценный winws на маке нереалистичен.

**Вывод по macOS:** реалистичная мак-версия — это «всё, кроме DPI-обхода»: прокси (sing-box) + Telegram-прокси + DNS + hosts + проверки. Именно прокси, а не winws, — рабочий способ обхода на маке.

Порядок внедрения: сначала платформенный слой + перенести «лёгкие» (прокси, tg, проверки) на Linux/macOS, затем hosts/DNS/элевация, в последнюю очередь — `nfqws2`-бэкенд для Linux.

## Архитектура

- `modules/` — вся логика (hosts, dns_jumper, domains, tgproxy, winws, cheburcheck). Интерфейсы — тонкие обёртки.
- `upstream/` — сабмодули внешних проектов (zapret2, tg-ws-proxy); их код импортируем/запускаем, но не правим — обновления через `git submodule update --remote`.
- `bin/zapret-win-bundle/` — бинарный бандл winws/winws2 + lua + WinDivert (в gitignore, тянется отдельно; держать COMPAT_VER одинаковым с сабмодулем zapret2).
- `strategies/` — портированные стратегии (`*.txt`), их fake-блобы (`assets/`) и hostlist'ы (`hostlists/`).
- `lists/` — списки доменов по сервисам, один файл = один сервис.
- `ui/` — `api.py` (все методы для фронта, без привязки к движку) + `hub.py` (пуш состояния модулей) + `backend_qt.py` / `backend_webview.py` / `backend_browser.py` (окно/вкладка и мост) + `web/` (фронт: `js/core.js`, `js/pages/*`, `css/base.css`). Мосты асинхронные: вызов уходит в фоновый поток, ответ возвращается по callId.
- Режим интерфейса: `config.json` → `"ui"` | `"tui"` | `"service"`; движок окна: `ui_backend` → `"pyside6"` | `"pywebview"` (в сборку exe входит только PySide6, см. `build.bat`).
- Транспорты (DNS-подмена / VPN / zapret) — поверх общих списков доменов, выбираются правилами.
