# Релизы и обновления

Как Chimera собирается, выкладывается и обновляется у пользователей.

## Коротко

- Пользователь качает zip со страницы Releases, распаковывает, запускает `Chimera.exe`. Python и git ему не нужны.
- Релиз выпускается тегом: `git tag v0.2.0 && git push origin v0.2.0`. Остальное делает GitHub Actions.
- Тег с дефисом (`v0.3.0-beta.1`) публикуется как пре-релиз — его видят только те, кто выбрал бета-канал.
- Программа сама проверяет, вышла ли новая версия, а ставит её только по кнопке.

## Как выпустить релиз

1. Убедиться, что проверка CI на `main` зелёная.
2. `git tag v0.2.0 && git push origin v0.2.0` (бета — `v0.3.0-beta.1`).
3. Через 30–40 минут на странице Releases появится `Chimera-0.2.0-win64.zip`. Текст релиза — автоматический список изменений, его можно поправить руками.

Тег, который не разбирается как версия (`vtest`, `v1.2`), валит сборку на шаге «Версия из тега» — exe с несравнимой версией не выходит.

## Где что лежит

| Что | Где |
|-----|-----|
| версия программы | `modules/version.py` (`VERSION`, `parse`, `is_newer`, `file_version`) |
| подстановка версии из тега | `tools/set_version.py` |
| бинарники и `versions.json` для сборки | `tools/fetch_bins.py` |
| сборка | `build.bat` |
| CI | `.github/workflows/release.yml`, `.github/workflows/ci.yml` |
| проверка, скачивание, `apply.cmd` | `modules/selfupdate.py` |
| состояние, фоновая проверка, порядок установки | `ui/updater.py` |
| методы для фронта | `ui/api.py`: `selfupdate_state`, `selfupdate_check`, `selfupdate_install`; источник хаба `selfupdate` |
| интерфейс | `ui/web/js/pages/settings.js` (карточка «Обновление Chimera»), `ui/web/js/shell.js` (отметка у версии) |

## Версия

- Единственный источник — `modules/version.py`. В репозитории там `dev`: запуск из исходников — всегда разработческая версия, самообновление в ней выключено, а в интерфейсе номер выводится как есть, без `v`.
- В сборке CI подставляет версию из тега (`v0.2.0` → `0.2.0`) через `tools/set_version.py`. Руками в файле ничего не меняется.
- Сравнение — по semver: `0.3.0-beta.1 < 0.3.0-beta.2 < 0.3.0`, числа в пре-релизе сравниваются числами (`beta.10 > beta.2`).
- В свойствах exe (FileVersion) — четыре числа: `0.3.0-beta.1` → `0.3.0.1`, `0.3.0` → `0.3.0.0`, `dev` → `0.0.0.0`.

## Сборка (`build.bat`)

- Nuitka standalone → `build\Chimera\Chimera.exe`, иконка — `assets/logo/chimera.ico`.
- Бинарники заранее кладёт `python tools/fetch_bins.py` (и в CI, и локально; уже скачанное не трогает без `--force`):
  - sing-box — пиннутая версия из `modules/proxy/manager.py`, со сверкой SHA256;
  - zapret-win-bundle — на пиннутом коммите `BUNDLE_COMMIT`, в сборку идёт только `zapret-winws/` (4 МБ из 62: остальное — cygwin/blockcheck, программа их не использует).
- В сборку копируются только `bin\sing-box\sing-box.exe` и `bin\zapret-win-bundle\zapret-winws\`, а не весь `bin\`.
- Рядом с exe пишется `versions.json` — версии сабмодулей и бандла. В собранной программе git нет, и «Источники и обновления» берут версии оттуда, а не показывают «—».
- Последним шагом пишется `manifest.txt` — список всех файлов сборки. Самообновление считает своими только эти файлы: всё прочее в папке программы не трогает.
- `build.bat --post-only` — только шаги после Nuitka (переименовать `build\main.dist` в `build\Chimera`, скопировать бинарники, записать `versions.json` и `manifest.txt`) — чтобы проверить их без 20-минутной компиляции.
- `.bat` и `.cmd` хранятся с CRLF (`.gitattributes`): `cmd.exe` промахивается по `goto` в файлах с LF.

## GitHub Actions

`release.yml` — только на пуш тега `v*`, `windows-latest`:

1. checkout с сабмодулями;
2. Python 3.14, `pip install -r requirements-dev.txt`;
3. `pytest`;
4. версия из тега → `modules/version.py`;
5. `python tools/fetch_bins.py`;
6. `build.bat` (кэш Nuitka между сборками — `actions/cache`);
7. дымовой тест сборки `tools/smoke_build.py` (см. ниже) — сломанная сборка в релиз не уходит;
8. zip `Chimera-<версия>-win64.zip` через `shutil.make_archive`, внутри папка `Chimera/` (у `Compress-Archive` из Windows PowerShell 5.1 обратные слеши в именах записей);
9. `gh release create` с архивом; тег с дефисом — `--prerelease`.

`ci.yml` — на pull request и пуш в `main`: `ruff check .` и `pytest` на `windows-latest`, без сборки. Нужен, чтобы чужие PR проверялись до мержа.

Ветка одна — `main`. Бета — это тег на любом коммите, отдельная ветка под неё не нужна. Секреты не нужны: хватает встроенного `GITHUB_TOKEN`. Пока репозиторий приватный, минуты Actions идут из бесплатного лимита аккаунта, а минута на Windows считается за две.

## Самообновление

### Проверка

- Через 15 секунд после запуска и дальше раз в 6 часов (переключатель «Проверять обновления»), плюс кнопка «Проверить».
- Один запрос `GET /repos/emptyenemy/chimera/releases?per_page=30` для обоих каналов. Берётся самая свежая версия по semver (не по дате: хотфикс старой ветки не обгонит свежий релиз), черновики пропускаются, пре-релизы — только в бета-канале, релиз без архива `Chimera-*-win64.zip` не считается.
- SHA256 архива — из поля `digest` ассета. Нет контрольной суммы — кнопка неактивна: скачанное не с чем сверить.
- Без токена. Пока репозиторий приватный, GitHub отвечает 404 — «не удалось проверить: релизов не видно», программа не падает.
- Нашлась новая версия — одно уведомление за сессию и отметка у номера версии в шапке сайдбара; клик по ней ведёт в настройки.

### Установка — только по кнопке

Порядок выбран так, чтобы всё, что может упасть, случилось до того, как что-то погашено:

1. «Обновить до X» → подтверждение → архив качается в `data/update/download/` с прогрессом, SHA256 сверяется (не сошёлся — файл удаляется, программа работает дальше), архив распаковывается в `data/update/staged/`.
2. Файлы текущей версии из её `manifest.txt` копируются в `data/update/rollback/` — пока программа ещё работает. Не получилось (или `manifest.txt` нет) — обновление отменяется, ничего не тронуто.
3. Пишется `data/update/apply.cmd`. Если запущена фоновая служба — она останавливается (до 15 с). Программа гасит свои модули (winws2, sing-box), запускает скрипт отдельным процессом и закрывается.
4. `apply.cmd`:
   - ждёт выхода Chimera (не дольше 2 минут);
   - копирует новую версию поверх (`robocopy /E` — без удаления; `/R:2 /W:1` — занятый файл не ждётся бесконечно);
   - удаляет файлы, которые были в старом `manifest.txt`, а в новой версии их нет;
   - при ошибке копирования возвращает файлы из `rollback/` и удаляет то, что успело прийти с новой версией;
   - поднимает службу, если она работала, и запускает `Chimera.exe`;
   - пишет всё в `data/logs/update.log`.

Списки сайтов (`lists/`) пользователь правит прямо в программе, поэтому из релиза в них докладываются только новые файлы: уже лежащие не перезаписываются и не удаляются.

Своими обновление считает только файлы из `manifest.txt`. Поэтому и нет `robocopy /MIR`: он удалил бы в папке всё, чего нет в новой версии, — а программу могли распаковать и на рабочий стол, и рядом с ней лежат чужие файлы. Сверх того не перезаписываются пользовательские `config.json`, `strategies\hostlists\list-general-user.txt`, `ipset-user.txt`, `ipset-all.txt`, `ipset-all.txt.backup`, а `data\` в манифесте нет вовсе.

`rollback/` остаётся до следующего обновления — прежнюю версию можно вернуть руками, скопировав её поверх.

### Интерфейс

- «Настройки → Обновление Chimera»: текущая версия, статус (последняя / доступна X / скачивание с прогрессом / ошибка), «Проверить», «Обновить до X», ссылка «что нового» на страницу релиза, канал «Стабильный / Бета», переключатель «Проверять обновления».
- Из исходников видно, есть ли новая версия, но кнопка неактивна с подсказкой «обновляется через git».

## Проверка

- Юнит-тесты: версии и пре-релизы, выбор релиза по каналу, 404 и сеть, скачивание со сверкой SHA256, распаковка, порядок установки и остановка службы, `versions.json` в сборке.
- `apply.cmd` гоняется по-настоящему на временных папках (путь с пробелом и кириллицей): обновление с сохранением пользовательских файлов, чужие файлы рядом с программой — целы и при обновлении, и при откате, откат при занятом файле, отмена, когда текущую версию не сохранить.
- Workflow — `actionlint`; шаги `build.bat` после Nuitka — `build.bat --post-only` на фейковой сборке.
- Сборку целиком — `python tools/smoke_build.py`: копия `build\Chimera` начисто (без `data/` и `config.json`), запуск без окна и без UAC, вызовы всех модулей через интерфейс — стратегии и fake-блобы, sing-box, Telegram-прокси, hosts и Flowseal, DNS, списки, версии, самообновление. Систему не трогает: winws, TUN, hosts и DNS не запускаются, а если в системе уже работает прокси или winws — шаги, которые бы их перезапустили, пропускаются. В релизном workflow он идёт с `--full`: ещё и всё, что требует прав администратора и меняет систему, — запуск winws2, запись hosts, прокси в PAC и TUN, смена DNS, задача автозапуска (каждый шаг возвращает как было; локально `--full` запускать только на одноразовой машине).
- Проверить сборку до тега: Actions → Release → Run workflow. Это та же сборка и тот же полный дымовой тест, но без версии из тега и без публикации релиза.
