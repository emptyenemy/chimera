# Релизы и обновления

Как Chimera собирается, выкладывается и обновляется у пользователей.

## Коротко

- Пользователь качает zip со страницы Releases, распаковывает, запускает `Chimera.exe`. Python и git ему не нужны.
- Релиз собирается и выкладывается локально одной командой: `tools/release_local.py <версия> --publish`. GitHub Actions для выпуска не нужен.
- Тег с дефисом (`v1.1.0-beta.1`) публикуется как пре-релиз — его видят только те, кто выбрал бета-канал.
- Программа сама проверяет, вышла ли новая версия, а ставит её только по кнопке.

## Как выпустить релиз

1. Заметки `release-notes/<версия>.ru.md` и `.en.md` готовы, всё закоммичено и запушено в `main`.
2. Собрать и проверить, ничего не публикуя (около часа на три варианта):
   ```powershell
   build\build-env313\Scripts\python.exe tools/release_local.py 1.0.3
   ```
   Нужны Python 3.13 с Nuitka 4.2.2 (окружение `build\build-env313` или `.venv`, см. ниже), Node 22+ и `gh` с входом.
3. Если всё прошло — то же с `--publish` и `--skip-build`: архивы пересобираются из готовых папок и проверяются ещё раз, на HEAD ставится тег `v<версия>`, тег пушится, `gh release create` выкладывает три архива. Бета — версия с дефисом (`1.1.0-beta.1`), она публикуется пре-релизом.
4. На странице Releases появятся три архива: `Chimera-1.0.1-win64.zip`, `Chimera-1.0.1-win64-webview.zip` и `Chimera-1.0.1-win64-lite.zip`. Текст релиза берётся из `release-notes/<версия>.ru.md` и `.en.md`; те же заметки доступны в приложении и на лендинге.

Тег, который не разбирается как версия (`vtest`, `v1.2`), валит сборку на шаге «Версия из тега» — exe с несравнимой версией не выходит.

## Где что лежит

| Что | Где |
|-----|-----|
| версия программы | `modules/version.py` (`VERSION`, `parse`, `is_newer`, `file_version`) |
| подстановка версии из тега | `tools/set_version.py` |
| бинарники и `versions.json` для сборки | `tools/fetch_bins.py` |
| сборка | `build.bat` |
| CI | `.github/workflows/release.yml`, `.github/workflows/ci.yml` |
| проверка, скачивание, `apply.cmd` | `modules/selfupdate.py` |
| состояние, фоновая проверка, порядок установки | `ui/updater.py` |
| методы для фронта | `ui/api.py`: `selfupdate_state`, `selfupdate_check`, `selfupdate_install`; источник хаба `selfupdate` |
| интерфейс | `frontend/src/pages/settings/updates.tsx`, `frontend/src/components/app/sidebar.tsx` |

## Версия

- Единственный источник — `modules/version.py`. В репозитории там `dev`: запуск из исходников — всегда разработческая версия, самообновление в ней выключено, а в интерфейсе номер выводится как есть, без `v`.
- В сборке CI подставляет версию из тега (`v1.0.1` → `1.0.1`) через `tools/set_version.py`. Руками в файле ничего не меняется.
- Сравнение — по semver: `0.3.0-beta.1 < 0.3.0-beta.2 < 0.3.0`, числа в пре-релизе сравниваются числами (`beta.10 > beta.2`).
- В свойствах exe (FileVersion) — четыре числа: `0.3.0-beta.1` → `0.3.0.1`, `0.3.0` → `0.3.0.0`, `dev` → `0.0.0.0`.

## Сборка (`build.bat`)

Локальная сборка требует **Python 3.13 и Nuitka 4.2.2**. `build.bat` проверяет
их до сборки фронта и останавливается с понятной ошибкой при несовпадении.
DLL сканируются встроенным в Nuitka PE-анализатором
(`--experimental=force-dependencies-pefile`): скачивание Dependency Walker с
нестабильного `dependencywalker.com` не требуется. Этот режим закреплён вместе
с версией Nuitka; состав DLL и запуск проверяются в каждом готовом ZIP.
Рекомендуется чистое окружение: сторонние пакеты из общей установки Python
могут попасть в standalone через необязательные импорты.

```powershell
py -3.13 -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements-dev.txt
python tools/fetch_bins.py
.\build.bat lite
.\build.bat webview
.\build.bat qt
```

Отсутствие обязательных бинарников останавливает упаковку до замены прежней
папки сборки. `versions.json` использует постоянные пути источников вместо
переведённых названий; версия компонента сохраняется при переключении RU/EN.
Программа читает также старые файлы с английскими и русскими названиями.

- `Chimera.exe` — это и окно, и команда `chimera` (`modules/cli`): сборка `--windows-console-mode=attach` (вывод в консоль терминала, своего окна консоли нет) и без манифеста администратора: команды не спрашивают права на каждый вызов, а окно повышается само при старте (`main.py`, `auto_elevate`). Без аргументов в терминале exe печатает справку, двойной клик открывает окно; автозапуск и запуск после обновления зовут `--window` явно.
- Рядом с exe кладутся `skills/` и `AGENTS.md` (до `manifest.txt`, так что обновление их доставляет).
- Nuitka standalone → `build\Chimera`, `build\Chimera-webview` или `build\Chimera-lite`, иконка — `assets/logo/chimera.ico`.
- Бинарники заранее кладёт `python tools/fetch_bins.py` (и в CI, и локально; уже скачанное не трогает без `--force`):
  - sing-box — пиннутая версия из `modules/proxy/manager.py`, со сверкой SHA256;
  - zapret-win-bundle — на пиннутом коммите `BUNDLE_COMMIT`, в сборку идёт только `zapret-winws/` (4 МБ из 62: остальное — cygwin/blockcheck, программа их не использует).
- В сборку копируются только `bin\sing-box\` (`sing-box.exe` и `libcronet.dll` — без неё не работает NaiveProxy) и `bin\zapret-win-bundle\zapret-winws\`, а не весь `bin\`.
- Рядом с exe пишется `versions.json` — версии сабмодулей и бандла. В собранной программе git нет, и «Источники и обновления» берут версии оттуда, а не показывают «—».
- Последним шагом пишется `manifest.txt` — список всех файлов сборки. Самообновление считает своими только эти файлы: всё прочее в папке программы не трогает.
- `build.bat [qt|webview|lite] --post-only` — только шаги после Nuitka (перенести `build\<вариант>\main.dist` в итоговую папку, скопировать бинарники, записать `versions.json` и `manifest.txt`) — чтобы проверить их без 20-минутной компиляции.
- `.bat` и `.cmd` хранятся с CRLF (`.gitattributes`): `cmd.exe` промахивается по `goto` в файлах с LF.

## Локальный выпуск (`tools/release_local.py`)

Повторяет шаги `release.yml` на своей машине: версия во `modules/version.py` на время сборки (потом возвращается), `build.bat` для каждого варианта, `Chimera.exe --version`, `tools/smoke_build.py` без `--full`, zip, `tools/verify_archive.py` и `tools/verify_upgrade.py` с последнего опубликованного релиза. Архивы, `checksums.txt` и текст релиза — в `build/release-<версия>/`. Окно программы проверки не открывают: запуск двойным кликом (`tools/smoke_launch.py`) — с флагом `--window`. Системные проверки `--full` локально не запускаются: они меняют hosts, DNS и TUN.

Скрипт отказывается работать с незакоммиченными правками (exe должен совпадать с коммитом), а с `--publish` — и пока HEAD не в `origin/main`, или если тег версии уже стоит на другом коммите.

## GitHub Actions

`release.yml` — только вручную (Actions → Release → Run workflow), `windows-latest`; пуш тега его не запускает. `pytest` в нём нет — он уже прошёл в `ci.yml` на том же коммите; `PYTHONUTF8=1` — консоль раннера в cp1252:

1. checkout с сабмодулями;
2. Python 3.13, `pip install -r requirements-dev.txt`;
3. версия из тега → `modules/version.py`;
4. `python tools/fetch_bins.py`;
5. `build.bat qt|webview|lite` в трёх параллельных задачах (кэш Nuitka между сборками — `actions/cache`);
6. дымовой тест сборки `tools/smoke_build.py` (см. ниже) — сломанная сборка в релиз не уходит;
7. zip, проверка структуры, манифеста, CLI и интерфейса после распаковки; загрузка артефакта только после проверок. Имена — `Chimera-<версия>-win64[-webview|-lite].zip` через `shutil.make_archive`, внутри папка соответствующего варианта (`Chimera/`, `Chimera-webview/`, `Chimera-lite/`) (у `Compress-Archive` из Windows PowerShell 5.1 обратные слеши в именах записей);
8. отдельная задача ждёт все три сборки, проверяет настоящее обновление архива 1.0.1 через `tools/verify_upgrade.py` с сохранением пользовательских файлов и резервной копией; затем вычисляет SHA256 и вызывает `gh release create` с тремя архивами; тег с дефисом — `--prerelease`.

`ci.yml` — на pull request и пуш в `main`: `ruff check .` и `pytest` на `windows-latest`, без сборки. Нужен, чтобы чужие PR проверялись до мержа.

Ветка одна — `main`. Бета — это тег на любом коммите, отдельная ветка под неё не нужна. Секреты не нужны: хватает встроенного `GITHUB_TOKEN`. Репозиторий публичный: минуты стандартных раннеров GitHub, включая Windows, не тарифицируются.

## Самообновление

### Проверка

- Через 15 секунд после запуска и дальше раз в 6 часов (переключатель «Проверять обновления»), плюс кнопка «Проверить».
- Один запрос `GET /repos/emptyenemy/chimera/releases?per_page=30` для обоих каналов. Берётся самая свежая версия по semver (не по дате: хотфикс старой ветки не обгонит свежий релиз), черновики пропускаются, пре-релизы — только в бета-канале, релиз без архива своего варианта (`win64.zip`, `win64-webview.zip` или `win64-lite.zip`) не считается.
- SHA256 архива — из поля `digest` ассета. Нет контрольной суммы — кнопка неактивна: скачанное не с чем сверить.
- Без токена: репозиторий публичный. Если GitHub отвечает 404 или недоступен — «не удалось проверить», программа не падает.
- Нашлась новая версия — одно уведомление за сессию и отметка у номера версии в шапке сайдбара; клик по ней ведёт в настройки.

### Установка — только по кнопке

Порядок выбран так, чтобы всё, что может упасть, случилось до того, как что-то погашено:

1. «Обновить до X» → подтверждение → архив качается в `data/update/download/` с прогрессом, SHA256 сверяется (не сошёлся — файл удаляется, программа работает дальше), архив распаковывается в `data/update/staged/`.
2. Файлы текущей версии из её `manifest.txt` копируются в `data/update/rollback/` — пока программа ещё работает. Не получилось (или `manifest.txt` нет) — обновление отменяется, ничего не тронуто.
3. Пишется `data/update/apply.cmd`. Если запущена фоновая служба — она останавливается (до 15 с). Программа гасит свои модули (winws2, sing-box), запускает скрипт отдельным процессом и закрывается.
4. `apply.cmd`:
   - ждёт выхода Chimera (не дольше 2 минут);
   - копирует новую версию поверх (`robocopy /E` — без удаления; `/R:2 /W:1` — занятый файл не ждётся бесконечно);
   - удаляет файлы, которые были в старом `manifest.txt`, а в новой версии их нет;
   - при ошибке копирования возвращает файлы из `rollback/` и удаляет то, что успело прийти с новой версией;
   - поднимает службу, если она работала, и запускает `Chimera.exe`;
   - пишет всё в `data/logs/update.log`.

Списки сайтов (`lists/`) пользователь правит прямо в программе, поэтому из релиза в них докладываются только новые файлы: уже лежащие не перезаписываются и не удаляются.

Своими обновление считает только файлы из `manifest.txt`. Поэтому и нет `robocopy /MIR`: он удалил бы в папке всё, чего нет в новой версии, — а программу могли распаковать и на рабочий стол, и рядом с ней лежат чужие файлы. Сверх того не перезаписываются пользовательские `config.json`, `strategies\hostlists\list-general-user.txt`, `ipset-user.txt`, `ipset-all.txt`, `ipset-all.txt.backup`, а также слоты фейков `strategies\assets\ACTIVE_DISCORD_UDP.bin` и `ACTIVE_GAME_UDP.bin` (релиз приносит значение по умолчанию, а выбранный под провайдера блоб копируется прямо в слот — обновление его не сбрасывает), а `data\` в манифесте нет вовсе.

`rollback/` остаётся до следующего обновления — прежнюю версию можно вернуть руками, скопировав её поверх.

### Интерфейс

- «Настройки → Обновление Chimera»: текущая версия, статус (последняя / доступна X / скачивание с прогрессом / ошибка), «Проверить», «Обновить до X», ссылка «что нового» на страницу релиза, канал «Стабильный / Бета», переключатель «Проверять обновления».
- Из исходников видно, есть ли новая версия, но кнопка неактивна с подсказкой «обновляется через git».

## Проверка

- Юнит-тесты: версии и пре-релизы, выбор релиза по каналу, 404 и сеть, скачивание со сверкой SHA256, распаковка, порядок установки и остановка службы, `versions.json` в сборке.
- `apply.cmd` гоняется по-настоящему на временных папках (путь с пробелом и кириллицей): обновление с сохранением пользовательских файлов, чужие файлы рядом с программой — целы и при обновлении, и при откате, откат при занятом файле, отмена, когда текущую версию не сохранить.
- Workflow — `actionlint`; шаги `build.bat` после Nuitka — `build.bat --post-only` на фейковой сборке.
- Сборку целиком — `python tools/smoke_build.py`: копия `build\Chimera` начисто (без `data/` и `config.json`), запуск без окна и без UAC, вызовы всех модулей через интерфейс — стратегии и fake-блобы, sing-box, Telegram-прокси, hosts и Flowseal, DNS, списки, версии, самообновление. Пока окно работает, те же процессы проверяются командной строкой exe (`--version`, `agent-info --json`, `status --json`, `winws state --json`, `lists show --json`): это сквозная проверка режима консоли attach и канала управления. Систему не трогает: winws, TUN, hosts и DNS не запускаются, а если в системе уже работает прокси или winws — шаги, которые бы их перезапустили, пропускаются. В релизном workflow он идёт с `--full`: ещё и всё, что требует прав администратора и меняет систему, — запуск winws2, запись hosts, прокси в PAC и TUN, смена DNS, задача автозапуска (каждый шаг возвращает как было; локально `--full` запускать только на одноразовой машине).
- Проверить сборку до тега: Actions → Release → Run workflow. Указать поле `version` (например, `1.0.1`): создаются три архива с этой версией, проходит полный дымовой тест и переход с 1.0.1. Артефакты доступны в Actions; релиз не публикуется.

### Проверка именно ZIP

```powershell
python tools/verify_archive.py Chimera-1.0.3-win64-lite.zip --flavor lite --version 1.0.3
```

Проверяется распакованный архив в пути с кириллицей и пробелами: точное
соответствие манифесту, необходимые бинарники, интерфейс, переводы и данные;
затем версия exe, CLI, все страницы меню и операции модулей. WebView2 проходит
как HTTP-проверку, так и проверку нативного окна. Версии компонентов проверяются
на русском и английском. Этот сценарий входит в Release workflow.

Перед проверкой функций `tools/smoke_launch.py` запускает exe через
`ShellExecuteExW("open")`: без аргументов, консоли, настроек и каталога данных.
Путь содержит кириллицу и пробелы. Проверяются видимое окно Windows, повторный
двойной клик без второго окна, интерфейс, CLI и клавиатурное меню TUI.
Для WebView проверяется путь процессов движка: строго `bin/webview2` из архива.
Для Lite дополнительно проверяется отсутствие Edge/Chrome с переходом на этот
движок. Тестовая переменная отсутствия браузера действует только с
`CHIMERA_SMOKE=1`. Проверка остаётся обязательной независимо от headless-тестов.
`--screenshot <путь.png>` сохраняет интерфейс настоящего видимого окна; для Lite
рядом появляется `<имя>-fallback.png`.

Все варианты при двойном клике открывают окно, включая старые настройки
`interface=service/tui`. Фоновый режим запускается явно: `service run`.
На чистой установке UAC не запрашивается; кнопка «Права администратора»
перезапускает окно для системных действий, отмена UAC оставляет окно открытым.
Непредвиденная ошибка запуска записывается в `%LOCALAPPDATA%/Chimera/startup.log`
и показывает сообщение средствами Windows.

WebView и Lite включают полный Fixed Version WebView2 x64, версия и SHA256
закреплены в `tools/fetch_webview.py`. Установка движка в Windows и загрузка
во время запуска не требуются. Архивы выросли из-за комплекта Chromium.
Целевая платформа — Windows 10/11 x64. На Windows 10 папке переносимого
движка выдаётся требуемое Microsoft право чтения AppContainer; это локальная
папка приложения. [Правила Microsoft для Fixed Version Runtime](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/distribution).

В выводе `SKIP` означает пропущенный шаг: работающие в системе winws/sing-box
не перезапускаются. Системные действия без `--full` не выполняются. Полная
проверка возможна только на отдельном одноразовом Windows-раннере: нельзя
считать пропущенный шаг успешной проверкой обхода в сети пользователя.

## Варианты

| Команда | Папка | Интерфейс |
|---|---|---|
| `build.bat qt` | `build/Chimera` | Qt с собственным Chromium |
| `build.bat webview` | `build/Chimera-webview` | переносимый WebView2, нативный WinAPI-трей |
| `build.bat lite` | `build/Chimera-lite` | отдельное окно Edge/Chrome; без браузера — переносимый WebView2 |

Во всех вариантах есть CLI, TUI и собранный интерфейс. Node 22+ обязателен только при сборке. `tools/set_flavor.py` создаёт временный модуль варианта для Nuitka, `tools/finish_build.py` упаковывает переносимую папку и манифест. Самообновление выбирает архив по встроенному `FLAVOR`.

Дымовая проверка: `python tools/smoke_build.py <папка> --flavor qt|webview|lite`. Qt запускается offscreen; WebView2/Lite проверяются через HTTP-мост и headless Edge. Автоматические системные действия отключены переменной `CHIMERA_SMOKE=1`; `--full` разрешает явные проверки системных изменений только на одноразовом CI-раннере.

**1.0.1 опубликована 30 сентября 2026 года:** [релиз и три архива](https://github.com/emptyenemy/chimera/releases/tag/v1.0.1).

Сборка использует **Python 3.13 и Nuitka 4.2.2**. На Python 3.14.7 пробный Lite
падал до входа в программу с `EOFError: marshal data too short`. Сбой воспроизведён
на маленьком примере с аннотациями, экспериментальный обход ломал `dataclass`.
Поэтому сборка и CI переведены на 3.13.
